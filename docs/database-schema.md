# OneSeat - Database Schema

## 1. Scope

This document records the Day 5 database design. It defines table ownership, important columns, constraints and indexes. SQL migrations and implementation details are added when the services are built.

One PostgreSQL container hosts three separate databases:

| Database | Owner | Purpose |
|---|---|---|
| `booking_db` | booking-service | Events, seats, bookings, idempotency records and outbox events |
| `payment_db` | payment-service | Payments and charge idempotency |
| `notification_db` | notification-service | Processed Kafka events |

Services must not read another service's database. There are no cross-database foreign keys.

## 2. Design conventions

- Primary identifiers are UUIDs generated by the application.
- Timestamps use `TIMESTAMPTZ` and are stored in UTC.
- Money is stored as integer minor units (`amount_cents`), not floating-point values.
- Redis stores temporary holds. A Hold is not a PostgreSQL table.
- PostgreSQL in `booking_db` is the source of truth for booked seats.

## 3. booking_db

### `events`

Stores events created by organizers.

| Column | Purpose |
|---|---|
| `id` | Primary key (UUID) |
| `name` | Event name |
| `starts_at` | Event start time |
| `seat_count` | Number of seats generated for the event |
| `created_at` | Creation timestamp |

Constraints: primary key on `id`; `seat_count` must be positive.

### `seats`

Stores the seats belonging to an event. Seat availability is derived from active holds in Redis and active booking-seat claims; it is not stored as a seat status column.

| Column | Purpose |
|---|---|
| `id` | Primary key (UUID) |
| `event_id` | Owning event |
| `label` | Seat label within the event |
| `created_at` | Creation timestamp |

Constraints: foreign key to `events`; unique `(event_id, label)`; unique `(event_id, id)` to support the composite reference from `booking_seats`.

### `bookings`

Stores the booking and its lifecycle status.

| Column | Purpose |
|---|---|
| `id` | Primary key (UUID) |
| `event_id` | Event being booked |
| `user_id` | User who owns the booking |
| `status` | `PENDING`, `CONFIRMED`, `FAILED` or `EXPIRED` |
| `amount_cents` | Booking amount in minor currency units |
| `created_at` | Creation timestamp |
| `updated_at` | Last status/update timestamp |

Constraints: foreign key to `events`; status restricted to the four defined values; amount must be non-negative; unique `(id, event_id)` to support the composite reference from `booking_seats`.

### `booking_seats`

Stores one row for each seat included in a booking. A booking can contain up to four rows.

| Column | Purpose |
|---|---|
| `booking_id` | Owning booking |
| `event_id` | Event for the seat |
| `seat_id` | Seat claimed by the booking |
| `created_at` | When the seat was claimed |
| `released_at` | Null while the claim is active; set when a FAILED or EXPIRED booking releases it |

Constraints and indexes:

- Primary key `(booking_id, seat_id)`.
- Foreign key `(booking_id, event_id)` references `bookings(id, event_id)`.
- Foreign key `(event_id, seat_id)` references `seats(event_id, id)`.
- Partial unique index on `(event_id, seat_id)` where `released_at IS NULL`.

The partial unique index allows only one active booking claim for a seat. `PENDING` and `CONFIRMED` bookings keep `released_at` null and therefore count as active. When a booking becomes `FAILED` or `EXPIRED`, the service sets `released_at` for its seat rows in the same database transaction as the status change. The historical rows remain available, while the seat can be claimed by a later booking.

The service must keep booking status and `released_at` consistent in the same transaction; the partial index enforces the seat-claim uniqueness rule.

### `idempotency_records`

Stores the result of a booking confirmation so a retry can return the original response.

| Column | Purpose |
|---|---|
| `endpoint` | Endpoint whose request is being made |
| `idempotency_key` | Value supplied in the `Idempotency-Key` header |
| `user_id` | User associated with the request |
| `request_hash` | Hash of the request body |
| `response_status` | HTTP status of the stored response |
| `response_body` | Stored response body (`JSONB`) |
| `created_at` | Creation timestamp |

Constraint: composite primary key `(endpoint, idempotency_key)`. Reuse of the same key and endpoint with a different request hash is rejected. The same key can be used on a different endpoint because the key is scoped by endpoint.

### `outbox_events`

Stores events that must be published to Kafka after the booking transaction commits.

| Column | Purpose |
|---|---|
| `id` | Primary key / event identifier (UUID) |
| `aggregate_id` | Booking ID used as the Kafka key |
| `event_type` | Event type, initially `booking.confirmed` |
| `payload` | Event payload (`JSONB`) |
| `created_at` | Creation timestamp |
| `published_at` | Null until successfully published |

The outbox row is inserted in the same transaction that confirms the booking. A publisher sends unpublished rows and records `published_at` after successful publication.

## 4. payment_db

### `payments`

Stores the simulated charge result. Payment-service owns this table; `booking_id` is an external identifier and has no foreign key to `booking_db`.

| Column | Purpose |
|---|---|
| `id` | Primary key (UUID) |
| `booking_id` | Booking identifier supplied by booking-service |
| `idempotency_key` | Charge idempotency key; booking ID is used as the key |
| `request_hash` | Detects reuse of the key with a different charge request |
| `amount_cents` | Charge amount in minor currency units |
| `status` | `SUCCEEDED`, `FAILED` or `TIMED_OUT` |
| `provider_ref` | Simulated provider reference, when available |
| `created_at` | Creation timestamp |
| `updated_at` | Last status/update timestamp |

Constraints: unique `booking_id`; unique `idempotency_key`; amount must be non-negative; status restricted to the defined values. A repeated charge for the same booking returns the stored result instead of creating another charge. A repeated key with a different request hash is rejected.

`GET /charges/{bookingId}` is used by booking-service to reconcile a stale `PENDING` booking. A transport timeout alone must not be treated as proof that no charge happened; the stored payment result is checked through the payment API.

## 5. notification_db

### `processed_events`

Records Kafka messages already handled by notification-service.

| Column | Purpose |
|---|---|
| `event_id` | Kafka event identifier |
| `topic` | Topic from which the event was consumed |
| `processed_at` | Processing timestamp |

Constraint: composite primary key `(event_id, topic)`. A repeated delivery with the same event ID and topic is ignored.

## 6. Index summary

| Database | Table | Index |
|---|---|---|
| `booking_db` | `seats` | Unique `(event_id, label)`; supports event seat lookup |
| `booking_db` | `bookings` | `(event_id, status)` for event booking queries |
| `booking_db` | `bookings` | `(status, updated_at)` for stale `PENDING` reconciliation |
| `booking_db` | `booking_seats` | Partial unique `(event_id, seat_id)` where `released_at IS NULL` |
| `booking_db` | `idempotency_records` | Primary key `(endpoint, idempotency_key)` |
| `booking_db` | `outbox_events` | Partial index for unpublished rows, ordered by `created_at` |
| `payment_db` | `payments` | Unique `booking_id` and unique `idempotency_key` |
| `notification_db` | `processed_events` | Primary key `(event_id, topic)` |

## 7. Booking-seat lifecycle decisions

| Booking status | `booking_seats.released_at` | Seat claim |
|---|---|---|
| `PENDING` | `NULL` | Active; prevents another booking from claiming the seat |
| `CONFIRMED` | `NULL` | Active; seat is sold |
| `FAILED` | Set | Released; seat can be booked again |
| `EXPIRED` | Set | Released; seat can be booked again |

A Redis hold is temporary and expires after five minutes. It is not persisted in PostgreSQL. During confirmation, the booking transaction creates the `PENDING` booking and its booking-seat rows; the database uniqueness rule remains the final protection against two bookings claiming the same seat.
